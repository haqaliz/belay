## 4. Testing strategy

- The flipped compose test is the acceptance; `docker compose config -q` validates
  syntax; the docker CI job builds it on the pinned runner.
- The in-image engine presence is asserted by the health endpoint's engine version
  field (or a `docker run` `belay --help` check like `tests/test_docker_image.py:88-94`).

## 5. Environment & determinism

- Docker-only (the docker CI job substrate). No network beyond the build's npm/pip
  fetches inside the image build (the engine image's multi-stage pattern already does
  this); the runtime container serves localhost only.

## 6. Edge cases & error handling

- **Health endpoint unreachable at compose start** — the healthcheck retries per
  compose semantics; the static server is up before the SPA loads (test the endpoint
  directly in the docker run check).
- **Engine missing in-image** — the health endpoint reports it (never claims ok); the
  console's no-engine state (A2's tested path) renders honestly.

## 7. Agent execution notes

- The engine image's Dockerfile + `tests/test_docker_image.py` are the templates —
  read them first.
- Do not touch the `belay` service's existing behavior (the compose regression test
  guards it); only add the console service and the shared volume wiring.
- The docker CI job's in-image suite (`tests/test_docker_inimage.py`) must keep
  passing — the console image is validated by the flipped compose test + a docker-run
  health check, not by re-running the whole suite in yet another container (bandwidth).
