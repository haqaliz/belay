# Implementation Plan — `mint-entrypoints`

**Date:** 2026-07-23 · **Aspect:** 2 of 5 · **Branch:** `feat/phase0-mint-execution/aliz`
**Spec:** `docs/planning/phase0-mint-execution/mint-entrypoints/spec.md`
**PRD:** `docs/planning/phase0-mint-execution/prd.md`
**Baseline:** 632 passed, 1 skipped, 1 deselected (aspect 1 merged at `dbcb409`). Keep green
at every phase.

This aspect is **not greenfield and not a core-engine change**. `uv sync` already works;
`eval/` exists and its parts (`batch`, `session`, `workspace`, `bridge`, `checkpoint`,
`servers`, `capture`, `clients/`) are built, tested, and proven end-to-end by Stage 1. The
only thing missing is **the committed program that calls them**. Everything here lands under
`eval/`, plus one docs file. **No `src/belay/` change** (aspect 1 already shipped what the
mint needs from the engine).

**The guardrail, restated because it is the one thing that could go wrong architecturally:**
`eval/` is not a product surface and must never become a `belay` CLI subcommand
(`eval/README.md:3-5`, `CLAUDE.md` guardrail #1). The entry point is invoked as
`python -m eval.minting_driver ...`, never as `belay mint ...`. The driver stays thin and
sequential — no planning, no memory, no retry-with-reflection.

## 1. Design decisions (resolve before coding)

### D1 — One code path: the one-instance tool **is** `run_mint` over a one-record list

The spec asks for two entry points. Implement them as **one** function with a filtered record
list, not two pipelines:

```
mint_one(instance_id, cfg)  ->  mint_batch([the one matching record], cfg)  ->  run_mint(...)
```

**Why this and not a separate single-instance path:** Stage 1's whole value was that it
rehearsed the batch path before the batch was run. A bespoke single-instance pipeline would
rehearse *itself* and prove nothing about Stage 3 — precisely the failure mode that made
`scratchpad/drive_one.py` worthless the moment it was deleted. One path also means the
resume, error-containment, bridge, and checkpoint semantics are literally identical, so
`test_batch_entrypoint_resumes_from_checkpoint` covers the single-instance path for free.

**Consequence to accept:** `mint_one` inherits `run_mint`'s resume semantics — an instance
already recorded `captured` in the checkpoint is **skipped**, and re-minting into a used
`root` would hit `BridgeCollisionError` anyway (`bridge.py:128-138`). See D5.

### D2 — Provider selection is an **argument**, never an environment sniff

Today the only provider selection in the repo is `tests/test_minting_driver_smoke.py:228-243`:
*"Anthropic if `ANTHROPIC_API_KEY` is set, else the local OpenAI-compat client if
`OPENAI_BASE_URL` is set, else skip."* That is the exact hazard the spec names — a stray key
in the shell silently switches which model mints, and the published number would then name
the wrong model.

**Rule:** `entrypoint.py` contains **no branch on the presence of any API-key variable.**
`--provider {openai-compat,anthropic}` is an explicit argument with an explicit default of
`openai-compat`; environment variables supply **credentials only**, never the choice.
`--model` defaults to `gemini-flash-latest` (the decided provider, `prd.md:205-208`).

This is testable two ways and both are cheap, so do both:

- **behavioural** — with `ANTHROPIC_API_KEY` set in a monkeypatched environment,
  `make_model_factory(provider="openai-compat", ...)` still builds a `LocalOpenAICompatModel`;
- **structural** — assert the string `ANTHROPIC_API_KEY` does not appear in
  `entrypoint.py`'s source. A behavioural test proves this build; the structural one prevents
  the sniff from being reintroduced. (Follow the precedent of
  `tests/test_minting_driver_transport.py::test_transport_module_is_standalone`, which already
  asserts a source-level property by AST.)

**Second, quieter hazard, fixed here:** `LocalOpenAICompatModel` substitutes
`LOCAL_SENTINEL_API_KEY` when `OPENAI_API_KEY` is unset (`local_client.py:73-75`). That is
right for Ollama and **wrong for Gemini**, where it produces a 401 on the first call of every
instance — 65 contained failures and an empty mint. The preflight (D4) therefore requires
both `OPENAI_BASE_URL` and a non-empty `OPENAI_API_KEY` for `--provider openai-compat`, and
says so by name.

### D3 — `request_timeout` is tightened in **both** places; `None` stops being reachable

`run_mint(request_timeout=...)` is keyword-only with **no default**, but its type is
`Optional[float]` and `None` falls through `run_session` → `run_task` → `transport.request`'s
`DEFAULT_TIMEOUT = 10.0` (`transport.py:53, 245`). Ten seconds is too tight for a live model
turn plus a cold `node` start under Seatbelt.

**Decision: enforce at the entry point AND narrow `run_mint`'s parameter to `float`.**

- `entrypoint.py` carries `DEFAULT_REQUEST_TIMEOUT = 120.0` and never forwards `None`.
- `batch.run_mint`'s annotation becomes `request_timeout: float`, and it raises a named
  `ValueError` on `None` or on a non-positive value.

**The cost, stated:** 7 call sites in `tests/test_minting_driver_batch.py` currently pass
`request_timeout=None` (lines 218, 254, 281, 313, 355, 387, 447, 461 — one of which is
`45.0`). They must be edited to pass an explicit float. **That is a legitimate edit, not
test-fudging** — those tests assert nothing about the timeout except at line 398-421, which
already passes `45.0` and stays untouched.

**Why not entry-point-only:** the entry point is not the only conceivable caller of
`run_mint`, and leaving `None` meaningful in the library reopens the hole for the next one.
`run_session`/`run_task` keep `Optional[float]` — their `None` path is documented as
byte-identical to before the knob existed (`loop.py:88-91`) and they are genuinely lower-level.

### D4 — The preflight runs **before** the loop, because `run_mint` contains failures too well

`build_server_command` is called *inside* `run_mint`'s per-instance `try/except`
(`batch.py:174`), which is correct for a mint but wrong for a missing install: a missing
`eval/servers/` would record all 65 instances `failed` with the same message, produce an empty
batch dir, and read as **`INSTRUMENT SUSPECT`** — a fake PIVOT from a `npm install` that was
never run. The mint would take an hour to say "you forgot to install node modules."

So `mint_batch` calls `resolve_server_entrypoint("filesystem")` **once, at the top**, before
any registry load, any workspace prep, and any model construction. `MissingServerError`
already carries the exact command (`servers.py:135-149`); let it propagate unchanged rather
than re-wording it. The CLI turns it into exit code 2 with the message on stderr.

Test the *ordering*, not just the exception: assert the `prepare` spy and the model-factory
spy both recorded **zero** calls.

### D5 — Re-minting an instance: a fresh `--root`, not a checkpoint edit

Stage-1 re-mint (`prd.md` requirement 8) needs to run `pallets__flask-4045` again. Under D1
that instance is `captured` in the old checkpoint and would be skipped, and its bridge
destination already exists.

**Decision: the checkpoint path defaults to `<root>/checkpoint.json`**, so a new `--root` is
a genuinely fresh mint with a fresh ledger, and re-running the *same* root is an idempotent
resume. No `--force`, no `Checkpoint.forget()`. Deleting a recorded disposition is a way to
double-spend by accident and to lose the record of what already ran; a directory the operator
names explicitly is a better unit of "this is a new attempt."

Flag at execution if this proves annoying in practice — but do not add `--force` speculatively.

### D6 — The verify step uses `{workspace}`, and `run_batch(server_command_for=)` is **not** used

Aspect 1 added both `belay.replay.engine.WORKSPACE_PLACEHOLDER = "{workspace}"` and
`run_batch(server_command_for=...)`. For this mint the placeholder is the correct one, and
the runner's own docstring says why (`runner.py:107-115`): the trace already carries its
`source_root`, so restating it per trace is the redundancy that caused the original defect.
The mint's verify command is therefore **one static command**:

```
belay phase0 run <root>/batch \
  --ledger runs/phase0.json --corpus-dir corpus/local \
  --server node <abs entrypoint> {workspace}
```

(no `--` separator — `--server` is `nargs=REMAINDER`; `STAGE1_FINDINGS.md:120-123`).

`mint_batch` **always prints this exact command** on completion — that printed line is the
reproduce-the-number artifact the RUNBOOK is supposed to contain. An optional `--verify` runs
it in-process via `belay.phase0.runner.run_batch(server_command=[...])`.

**Import discipline:** `belay` is imported **lazily, inside** the verify function, and nowhere
else in `eval/`. `import eval.minting_driver.cli` must succeed with `belay` absent. Assert it
with a `sys.modules` check, mirroring `tests/test_minting_driver_clients_import.py`.

**Tests (write first):**

### Phase 7 — Docs: correct `eval/README.md` and document the commands

**Goal:** the reproduce-the-number path is written down, and the two inaccuracies found while
reading are fixed rather than inherited.

1. **Install-command mismatch.** `eval/README.md:79-83` documents
   `mkdir -p eval/servers && cd eval/servers && npm install <specs>`; `servers.py:113`
   generates `npm install --prefix <root> <specs>` and that generated string is what the error
   the operator will actually see says. Make the README quote the `--prefix` form so the two
   agree.
2. **"launched by absolute `node` path" is inaccurate** (`eval/README.md:39-40`, and the same
   claim in `CLAUDE.md`'s status block). `filesystem_server_command` returns
   `["node", str(entrypoint), str(allowed_dir)]` (`servers.py:162`) — only the *entrypoint* is
   absolute; `node` itself is a bare `$PATH` lookup. Reword to "launched by absolute
   *entrypoint* path". **Do not** change `servers.py` to resolve `node` absolutely in this
   aspect: that command is also the replay `--server` command, so changing it changes replay
   inputs, which is out of scope here. Record it as a follow-up observation instead.
3. Add a **"Running a mint"** section with the two `python -m eval.minting_driver` commands,
   the required env (`OPENAI_BASE_URL`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` **unset**), and
   the printed `belay phase0 run … {workspace}` verify command.
4. Note that `BELAY_EVAL_MODEL` is read **only** by the smoke test and is **not** an entry-point
   knob — `--model` is. (See §7 ambiguity 4.)

**Validation:** full suite green (docs-only); no behavior change.

**Commit:** `docs(eval): the committed mint commands, and two corrected claims`

### Phase 8 — (CUTTABLE) strengthen the manual smoke

PRD nice-to-have 22; the spec says "belongs here if it is cheap." **Cut this phase if
anything earlier ran long** — it is a `manual`-marked test that never runs in CI and never
gates a merge.

Two weaknesses, both of which let the Stage-1 false positive pass:

- the oracle accepts `VERIFIED_FLAGGED` (`test_minting_driver_smoke.py:314-318`), so a false
  FLAG *satisfied* it (`STAGE1_FINDINGS.md:77-79`);
- it bypasses `bridge_capture` with `manifest_dir_for=` (`:309`), so it never rehearses the
  layout the stock CLI resolves.

**Change:** re-point the smoke at `mint_one` + the default manifest resolution, and assert
**`VERIFIED_CLEAN`** for the known-correct edit, printing every flag's detail in the assertion
message so a legitimate flag is diagnosable rather than mysterious.

**The tradeoff, stated:** a genuinely-flagged turn (e.g. a real annotation-conformance finding)
would now fail the smoke. That is the intended trade — after aspect 1, a flag on this instance
is news, and a manual test that cannot tell news from noise is not an oracle.

**Validation:** full suite green with the smoke still deselected
(`uv run pytest --collect-only | grep smoke` prints nothing).

**Commit:** `test(eval): the manual smoke asserts a CLEAN verdict through the real bridge`

## 4. Testing strategy

- **Commands:** `uv run pytest` (full), `uv run pytest tests/test_minting_driver_entrypoints.py
  tests/test_minting_driver_cli.py -v` (aspect).
- **Every test is offline and deterministic.** Reuse the seam-injection vocabulary already
  established in `tests/test_minting_driver_batch.py` — `StubPrepare`, `OkTransport`,
  `CountingModelFactory`, `FailingOnInstance`, `discover_tools=lambda cmd: []`. Do not invent a
  second style; if a helper is needed in both files, import it or lift it to a shared module,
  but prefer duplication of ~15 lines over a premature shared fixture.
- **No git, no network, no subprocess, no model call, no spend** in CI. The registry is a tmp
  file written with `dump_registry`; the "installed server" is an empty file at the pinned
  entrypoint path.
- **No clock, no randomness.** Nothing in this aspect may read the wall clock; `run_mint`
  already doesn't, and `MintReport` must not stamp a timestamp (the trace filename already
  carries the gate's own).
- **The live path** stays `manual`-marked plus `BELAY_EVAL_LIVE=1` plus `sys.platform ==
  "darwin"` — three independent guards, unchanged.
- **Do not edit `tests/test_minting_driver_batch.py` to make anything pass**, except the
  mechanical `request_timeout=None` → float substitution D3 authorizes.

## 5. Edge cases → what the operator sees

This aspect emits **no verdicts** — it is a capture tool. But every failure here has a verdict
*consequence* downstream, and that is what the column below records.

| Case | Entry-point behavior | Downstream consequence if unhandled |
|---|---|---|
| `eval/servers/` absent | **Hard error before anything runs**, with the `npm install` command | 65 contained failures → empty batch → `INSTRUMENT SUSPECT` read as a PIVOT |
| `--registry` file absent | Named error pointing at the `instance-pool` aspect | `FileNotFoundError` traceback mid-setup |
| Unknown `instance-id` | Named error listing the record count | empty mint → `INSTRUMENT SUSPECT` |
| `OPENAI_API_KEY` unset, `--provider openai-compat` | Named error naming both variables | `LOCAL_SENTINEL_API_KEY` → 401 per instance → empty mint |
| Stray `ANTHROPIC_API_KEY` in the shell | **Ignored** — provider is an argument (D2) | the published number names the wrong model |
| `request_timeout` omitted | `120.0`; `None` rejected (D3) | 10s ceiling → `ReplyTimeout` on cold start → contained failures |
| One instance's server exits | Recorded `failed` with a reason, loop continues (`run_mint`, unchanged) | a whole mint dies at #37 |
| Re-mint into a used `--root` | `BridgeCollisionError` → that instance `failed` (D5) | a silently clobbered capture |
| Gate env incomplete | Impossible: `run_mint` always sets all three vars via `gated_env`, which itself refuses scope-without-snapshot | trace-only capture → every turn UNVERIFIED → `INSTRUMENT SUSPECT` |
| Model issues zero tool calls | `NoTraceError`/empty manifests → `NO_VERIFIABLE_TURNS`, instance stays in the ledger (`bridge.py:23-32`, unchanged) | the instance vanishes and the mint reads cleaner than it is |

**A silent success is never an acceptable fallback here.** Every path above either produces a
capture or says loudly why it didn't; nothing may quietly reduce the denominator.

## 7. Spec ambiguities and contradictions found in `eval/`

Flagged rather than silently resolved. Items 1–3 have a proposed resolution baked into the
phases above; 4–6 need a decision at execution.

1. **"resolves an id from the registry" — there is no registry file.** `selected.json` does not
   exist (it is the `instance-pool` aspect's deliverable) and `eval/instances.md` is prose with
   one entry. **Resolved:** `--registry` is an explicit path; its default is
   `eval/instances/selected.json` and its absence is a named error naming that aspect. The two
   aspects stay decoupled and can land in either order.
2. **The Stage-1 re-mint has no committed record to run against** until `instance-pool` lands.
   Cheapest fix, ~15 committed lines: a one-record `eval/instances/stage1.json` for
   `pallets__flask-4045` (its `base_commit` is already verified in `eval/instances.md`).
   **Proposed but not assumed** — skip it if `instance-pool` lands first.
3. **`run_mint`'s `Optional[float]` timeout vs the spec's "must not default to 10s".** D3
   narrows it to `float` and edits 7 test call sites. If the reviewer prefers not to touch
   `batch.py`, entry-point-only enforcement satisfies the letter of acceptance 2 but leaves the
   hole for the next caller. Stated so it is a choice, not an oversight.
4. **`BELAY_EVAL_MODEL` is read only by `tests/test_minting_driver_smoke.py:231,237`** — no
   `eval/` module reads it, yet `STAGE1_FINDINGS.md:128-130` documents it as part of the live
   recipe. The entry point uses `--model` instead. If phase 8 re-points the smoke at
   `mint_one`, this variable disappears from the repo entirely; otherwise two mechanisms
   coexist. **Decide at phase 8.**
5. **`eval/README.md:104-108` and `servers.py:113` disagree on the install command**
   (`cd && npm install` vs `npm install --prefix`). Phase 7 fixes the README, since the
   generated string is what the operator's error message will show.
6. **`eval/README.md` (and `CLAUDE.md`) claim servers are "launched by absolute `node` path".**
   They are not — `servers.py:162` emits a bare `node` plus an absolute *entrypoint*. Phase 7
   corrects the wording. Whether `node` itself should be resolved absolutely is a real question
   (it is also the replay `--server` command, so it affects replay inputs) and is deliberately
   **out of scope** here.
