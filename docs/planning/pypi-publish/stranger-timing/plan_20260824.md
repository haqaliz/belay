## 2. Implementation phases

### Phase 1: the runbook

- **Goal:** `runbook.md` written per the spec, so the post-merge operator step is a
  20-minute, reproducible procedure.
- **Prerequisites:** `quickstart-flip` merged into this branch (the runbook matches
  the flipped README; the checklist completion contract is its record target).
- **Files to create:** `docs/planning/pypi-publish/stranger-timing/runbook.md` with
  sections:
  1. **What this measures** — time-to-first-verdict: stopwatch starts at the first
     command of §3, stops when `belay verify` prints its first verdict line with the
     coverage line. Explicit so two timers agree. n=1 is a measurement, not a
     guarantee (honest-claims note).
  2. **Clean-box preconditions** — fresh macOS or Linux (a VM is fine, state it);
     Python 3.10–3.12; uv recommended, `pipx`/`pip` alternates; record the install
     path and Python version used.
  3. **The timed path (mirror the flipped README quickstart exactly)** —
     `uv tool install belay-harness` (or the pipx/pip alternate) → `belay --help` →
     the minimal capture → verify example: a tiny deterministic stdio MCP server
     (point at `tests/fixtures/docker_roundtrip_server.py` as the reference shape,
     or a two-line inline server), run through `python -m belay.proxy` with
     `BELAY_SANDBOX_SCOPE` / `BELAY_SNAPSHOT_DIR` / `BELAY_TRACE_DIR`, one
     `tools/call` that writes a file, then `belay verify <trace> --manifest-dir
     <snaps> --server ...` → the first verdict. Include a literal command block the
     stranger can paste.
  4. **The live-install check (not timed, network-dependent)** — the clean box
     installs the LIVE PyPI package (that is the point: CI only proves the local
     artifact); `belay --help`, `belay sandbox check --scope <tmp>` (named limits:
     Linux needs kernel ≥ 5.13 / Landlock; macOS uses Seatbelt).
  5. **Record** — write the number, environment, install path, timer identity
     (stranger vs owner — the checklist gate wants "one person", record who), and
     date into `docs/planning/launch-readiness/CHECKLIST.md` L4 and its progress
     log; then the operator marks L4 ✅ (the only act that checks the box).
- **Validation:** the runbook's install command equals the README headline command
  (verbatim, so the consistency test can compare strings).
- **Commit message:** `docs(timing): the time-to-first-verdict runbook (L4's remaining clause)`

## 4. Testing strategy

- The docs-consistency suite covers it (runbook exists + matches README). Manual
  verification: the operator runs the runbook once post-merge (that IS the metric).

## 5. Environment & determinism

- The runbook describes a network-dependent operator step (live PyPI install) — by
  design outside CI; the repo-side test remains deterministic (string comparison on
  committed files).

## 6. Edge cases & error handling

- **The timed stranger is unavailable (R10):** the runbook's record step explicitly
  supports "owner-measured n=1 following the exact runbook" as the degraded case and
  requires the record to name who timed it — the checklist gate stays honest either
  way.
- **Landlock unavailable on the stranger's Linux box:** the runbook's sandbox-check
  step documents the named-cause refusal (pre-5.13 kernel) as expected output, not
  failure — the honest-coverage line from README applies.

## 7. Agent execution notes

- The runbook's command blocks must be copy-paste correct: verify each command
  against the installed CLI on the local box (macOS) before committing — the
  `BELAY_*` env vars and the `--manifest-dir` flag spelling are load-bearing.
- Do not invent a new minimal server if the roundtrip fixtures suffice; point at
  `tests/fixtures/docker_roundtrip_server.py` as the reference and keep the runbook
  self-contained with an inline server if the fixture import path would confuse a
  stranger.
- No `src/` changes. No version bumps.
